# auction-router

Маршрутизатор аукционных запросов: принимает от площадки описание рекламного места,
отбирает по претаргетингу тех DSP-партнёров, кому это место подходит, приглашает их
всех разом с общим бюджетом времени и отвечает тем, что из этого вышло.

Только стандартная библиотека. Go 1.26.

## Как запустить

```sh
mise run run          # go run ./cmd/router
mise run check        # go vet + gofmt + go test -race
mise run cover        # покрытие по пакетам
mise run build        # бинарь в bin/router
```

Без mise — то же самое напрямую:

```sh
go run ./cmd/router
go test -race ./...
```

Флаги (`mise run run -- -log-level debug`):

| флаг         | по умолчанию    | что задаёт                                         |
|--------------|-----------------|----------------------------------------------------|
| `-addr`      | `:8080`         | адрес, на котором обслуживаются аукционы           |
| `-partners`  | `partners.json` | файл с описанием партнёров                         |
| `-budget`    | `200ms`         | сколько времени отведено одному раунду приглашений |
| `-log-level` | `info`          | `debug`, `info`, `warn` или `error`                |

Останавливается по `Ctrl-C` или `SIGTERM`: перестаёт принимать новые соединения и
даёт текущим аукционам до пяти секунд на завершение.

Проверка живости — `GET /health`:

```sh
curl -i -s localhost:8080/health | head -1
```

```
HTTP/1.1 204 No Content
```

Тела нет намеренно: у проверки здоровья весь ответ и есть код состояния, а `{"status":"ok"}`
был бы JSON, который никто не разбирает. Отдельной проверки готовности нет по той же
причине — она совпала бы с проверкой живости: реестр читается один раз при старте, и если
он не прочитался, сервис не начинает обслуживать вовсе. Шаблон маршрута обслуживает и
`HEAD`, а в лог эти запросы не пишутся, иначе проба раз в секунду забила бы его целиком.

## Пример: видно, что фильтрация работает

Берём один и тот же лот и меняем в нём **по одному полю** — каждый раз отсеивается
другой партнёр.

**Базовый запрос.** Проходят двое: `dsp-alpha` (Россия в списке, mobile в списке,
пол цены 0.5 ниже 1.5) и `dsp-delta`.

```sh
curl -s -X POST localhost:8080/auction \
  -d '{"request_id":"r-1","country":"RU","device_type":"mobile","bid_floor":1.5}'
```

```json
{
  "request_id": "r-1",
  "status": "ok",
  "matched_dsps": [
    "dsp-alpha",
    "dsp-delta"
  ],
  "sent": 2,
  "succeeded": 1,
  "duration_ms": 0
}
```

**Добавляем категорию `gambling`** — `dsp-alpha` её блокирует и выпадает:

```sh
curl -s -X POST localhost:8080/auction \
  -d '{"request_id":"r-2","country":"RU","device_type":"mobile","bid_floor":1.5,"categories":["gambling"]}'
```

```json
{
  "request_id": "r-2",
  "status": "ok",
  "matched_dsps": [
    "dsp-delta"
  ],
  "sent": 1,
  "succeeded": 0,
  "duration_ms": 0
}
```

**Поднимаем цену до 3.0** — теперь дотягивается `dsp-gamma` с порогом 2.0, и партнёров
становится трое:

```sh
curl -s -X POST localhost:8080/auction \
  -d '{"request_id":"r-3","country":"RU","device_type":"mobile","bid_floor":3.0}'
```

```json
{
  "request_id": "r-3",
  "status": "ok",
  "matched_dsps": [
    "dsp-alpha",
    "dsp-gamma",
    "dsp-delta"
  ],
  "sent": 3,
  "succeeded": 2,
  "duration_ms": 0
}
```

**Меняем страну на DE** — попадаем на `dsp-omega`, который не отвечает никогда.
Раунд заканчивается по бюджету, а не по нему: `duration_ms` — 201, и аукцион всё равно
отдал результат.

```sh
curl -s -X POST localhost:8080/auction \
  -d '{"request_id":"r-4","country":"DE","device_type":"mobile","bid_floor":1.5}'
```

```json
{
  "request_id": "r-4",
  "status": "ok",
  "matched_dsps": [
    "dsp-beta",
    "dsp-omega"
  ],
  "sent": 2,
  "succeeded": 1,
  "duration_ms": 201
}
```

**Никто не подошёл** — это штатный ответ, 200 с пустым списком и статусом
`no_matched_dsps`:

```sh
curl -s -X POST localhost:8080/auction \
  -d '{"request_id":"r-5","country":"JP","device_type":"tv","bid_floor":99}'
```

```json
{
  "request_id": "r-5",
  "status": "no_matched_dsps",
  "matched_dsps": [],
  "sent": 0,
  "succeeded": 0,
  "duration_ms": 0
}
```

**Негодный запрос** — 400, и все претензии сразу, а не первая по счёту:

```sh
curl -s -X POST localhost:8080/auction \
  -d '{"request_id":"r-6","country":"russia","device_type":"fridge","bid_floor":-1}'
```

```json
{
  "error": "request does not describe a lot the exchange can sell",
  "details": [
    "country: \"russia\" is not an ISO 3166-1 alpha-2 code",
    "device_type: \"fridge\" is not a known device type",
    "bid_floor: -1 is negative"
  ]
}
```

## Логи

Одна строка на запрос, на уровне `info`:

```json
{"level":"INFO","msg":"auction held","request_id":"r-1","country":"RU","device_type":"mobile","matched":2,"filtered":4,"succeeded":1,"duration_ms":0}
```

Причина, по которой отсеялся конкретный партнёр, — на `debug`. Это необязательный
пункт задания, и он вынесен на уровень, который в бою выключают: строк здесь столько,
сколько партнёров, то есть при 6 партнёрах и 100k RPS — 600 тысяч строк в секунду.

```sh
mise run run -- -log-level debug
```

```json
{"level":"DEBUG","msg":"partner passed over","request_id":"r-1","partner":"dsp-beta","term":"country"}
{"level":"DEBUG","msg":"partner passed over","request_id":"r-1","partner":"dsp-gamma","term":"bid_floor"}
{"level":"DEBUG","msg":"partner passed over","request_id":"r-1","partner":"dsp-omega","term":"country"}
{"level":"DEBUG","msg":"partner passed over","request_id":"r-1","partner":"dsp-epsilon","term":"enabled"}
{"level":"WARN","msg":"partner did not answer","request_id":"r-1","partner":"dsp-delta","error":"the partner answered with an error"}
```

Молчание приглашённого партнёра — это `warn`, а не `debug`: отсев по претаргетингу
работает как задумано, а здесь у кого-то авария. Отказ в запросе тоже пишется в лог,
иначе по логам не отличить «нас никто не зовёт» от «нас все зовут неправильно».

## Где лежат партнёры и как добавить нового

В `partners.json` в корне — массив объектов. Путь задаётся флагом `-partners`.

Сейчас там шесть партнёров, подобранных так, чтобы каждое правило претаргетинга
отсекало кого-нибудь:

| uid           | окончание | страны   | устройства      | пол цены | блокирует |
|---------------|-----------|----------|-----------------|----------|-----------|
| `dsp-alpha`   | `/ok`     | RU, KZ   | mobile, desktop | 0.5      | gambling  |
| `dsp-beta`    | `/ok`     | US, DE   | любые           | 0.1      | —         |
| `dsp-gamma`   | `/ok`     | любые    | mobile          | 2.0      | —         |
| `dsp-delta`   | `/error`  | RU       | mobile, tv      | 0        | —         |
| `dsp-omega`   | `/slow`   | DE       | любые           | 0        | —         |
| `dsp-epsilon` | `/ok`     | выключен |                 |          |           |

Минимальная запись — четыре обязательных поля:

```json
{
  "uid": "dsp-new",
  "name": "DSP New",
  "endpoint": "https://new.dsp.example/ok",
  "is_enabled": true
}
```

Остальное необязательно, и **пропуск означает отсутствие ограничения**: пустой или
отсутствующий список стран — «работаю со всеми странами», отсутствующий `min_bid_floor` —
«покупаю по любой цене».

Правило, по которому поля поделены: **обязательно то, у чего нет осмысленного значения
по умолчанию, либо то, чьё естественное умолчание тихо сделает не то.** `uid` и
`endpoint` без значения бессмысленны. `name` нужен человеку, который читает файл.
А `is_enabled` — единственный спорный: умолчание для него возможно, но опасно в любую
сторону. `encoding/json` молча игнорирует незнакомые ключи, поэтому опечатка вроде
`"enabled"` вместо `"is_enabled"` при умолчании `false` тихо выключила бы партнёра, а при
умолчании `true` — тихо включила и потратила деньги. Обязательность — единственный
вариант, при котором сервис не стартует и назовёт поле.

Файл проверяется целиком при старте, и все ошибки сообщаются разом, с адресом каждой:

```
reading partners from partners.json:
partners[2].uid: "" is empty or padded with whitespace
partners[3].countries[1]: "RUS" is not an ISO 3166-1 alpha-2 code
partners[5].uid: uid is claimed twice, first by partners[1]
```

Окончание адреса определяет, как партнёр ответит: `/slow` не отвечает до конца раунда,
`/error` отвечает ошибкой, **любое другое** (включая `/ok` и `/bid`) отвечает сразу.
Про это — в следующем разделе.

## Как устроено

```
cmd/router          конфигурация, сборка, мультиплексор, мягкое выключение
internal/auction    предметная область: лот, партнёр, реестр, претаргетинг, биржа
internal/api        HTTP: разбор запроса, хендлер, сериализация ответа, логи
internal/jsonfile   чтение партнёров из файла
internal/parsing    общее между чтением запроса и чтением файла
internal/fakedsp    подставные партнёры
```

Зависимости направлены внутрь. `internal/auction` не знает ни про HTTP, ни про JSON, ни
про то, где лежат партнёры. `internal/api` не знает, что делает лот подходящим. Про файл
знает только `internal/jsonfile`, и он упомянут в одном месте — в строке сборки в
`cmd/router`. Интерфейс `PartnerSource` объявлен **у потребителя**, в `cmd/router`, а не
рядом с реализацией: чтобы сменить хранилище на SQL, нужно реализовать один метод
`Load(ctx) ([]auction.Partner, error)` и поменять одну строку.

Приглашения уходят одновременно, каждое в своей горутине, и все получают **один общий
дедлайн** — не по дедлайну на партнёра. Паника внутри приглашения превращается в ошибку:
`http.Server` восстанавливается только на той горутине, где сам вызвал обработчик, но
никогда на тех, которые обработчик породил, так что необработанная паника здесь убила бы
процесс целиком. Если у вызывающего дедлайн ближе бюджета, раунд заканчивается по нему.

## Решения, которые стоит назвать вслух

**По сети мы не ходим.** Задание допускает три варианта, и выбран третий: DSP-клиент —
это интерфейс `auction.Inviter` с фейковой реализацией в `internal/fakedsp`, которая
смотрит на окончание адреса и отвечает сама. Настоящего HTTP-запроса партнёру нет.
Механизм при этом виден целиком: параллельность, общий таймаут и устойчивость к падению
отдельного партнёра проверены тестами `internal/auction` и воспроизводятся на живом
сервисе примерами выше.

**`duration_ms` бывает нулём, и это правда.** Без сетевых вызовов отбор шести партнёров
занимает меньше миллисекунды. Ненулевое значение появляется там, где раунд действительно
чего-то ждёт — 201 в примере с `dsp-omega`.

**В ответе есть `status`, которого нет в форме из задания.** Задание требует «явное
указание, что отправлять было некому»; поле `status` со значениями `ok` и
`no_matched_dsps` и есть это указание. Оно присутствует в **любом** успешном ответе, а не
только в пустом: смысл, закодированный в отсутствии поля, читатель обязан угадывать.

**`sent` всегда равен длине `matched_dsps`.** Здесь приглашение уходит каждому, кто прошёл
претаргетинг. В бою они разошлись бы — из-за ограничений частоты на партнёра или
разомкнутого предохранителя, — и тогда `sent` стал бы отдельным числом.

**Страна проверяется только по форме**, две заглавные латинские буквы, без сверки со
справочником ISO. Это намеренно: `XK` (Косово) в стандарте отсутствует, но его отдают и
MaxMind, и Евростат, а отвергнутый лот — это потерянные деньги.

**Тело запроса ограничено 64 КиБ**, и всё, что больше, получает `413`. У `net/http` нет
ограничения на тело по умолчанию — только на заголовки, — так что один клиент с
`curl -d @/dev/zero` иначе исчерпал бы память для всех.

## Чего здесь нет

Честный список того, что не сделано, чтобы это не выглядело недосмотром.

- **`internal/fakedsp` и `parseConfig` без тестов.** Первое — фикстура, её поломка видна
  в первую секунду запуска. Второе покрыто не было, и правило «бюджет должен быть
  положительным» держится только на самом коде.
- **Опечатка в имени ключа в `partners.json` проходит незамеченной.** `"country"` вместо
  `"countries"` — ключ молча выбрасывается, и партнёр начинает покупать во всех странах.
  Лечится `json.Decoder` с `DisallowUnknownFields`.
- **Окончание адреса сверяется точным суффиксом.** `/slow/` и `/slow?v=2` не совпадут и
  ответят как обычный партнёр.
- **Ответ партнёра не разбирается** — задание этого и не требует. Успех приглашения
  означает только, что партнёр ответил; отказ от покупки — тоже ответ, а не неудача.
- **Второй `Ctrl-C` во время выключения ничего не делает.** Перехват сигнала снимается
  только после того, как выключение закончилось.

## Что доделал бы, будь больше времени

**Настоящий HTTP-клиент к партнёрам** вместо фейка — с одним переиспользуемым
`http.Client`, обязательным вычитыванием и закрытием тела ответа (иначе соединение не
вернётся в пул), без поля `Timeout`, чтобы клиент не спорил с контекстом. Тесты — против
`httptest.NewServer`, где медленный и падающий партнёр настоящие.

**Метрики вместо логов для наблюдения.** При реальном потоке строку на запрос не пишут:
нужны счётчики по партнёрам и причинам отсева, гистограмма длительности раунда и доля
ответивших. Логи остаются для разбора конкретного случая.

**Предохранитель и ограничение частоты на партнёра.** Партнёр, который стабильно молчит,
не должен получать приглашения и тратить бюджет раунда. Отсюда же разошлись бы `sent` и
`matched_dsps`.

**Расширить `Inviter` до `(Result, error)`.** Сейчас невозможно отличить «партнёр ответил
и отказался» от «партнёр ответил и предложил цену»; для настоящего аукциона нужна ставка,
а значит и разбор ответа.

**Закрытый справочник категорий.** Сейчас категория — любая непустая строка без
обрамляющих пробелов, поэтому `"News"` и `"news"` для сопоставления разные. Правильное
решение — таксономия IAB с фиксированным набором идентификаторов.

**Перезагрузка партнёров без перезапуска** — по `SIGHUP` или по изменению файла, с
сохранением прежнего реестра при любой ошибке чтения.

**`matched_dsps` не отдавать площадке.** Список тех, кому ушёл запрос, — это внутреннее
устройство биржи, и в бою его показывают в отладочном режиме, а не всем.
